# HTRU2 Pulsar Pipeline

[![CI](https://github.com/VDgk465/htru2-pulsar-pipeline/actions/workflows/ci.yml/badge.svg)](https://github.com/VDgk465/htru2-pulsar-pipeline/actions/workflows/ci.yml)

A reproducible machine-learning pipeline that classifies pulsar candidates in the
[HTRU2 dataset](https://archive.ics.uci.edu/dataset/372/htru2) (17,898 signals, ~9% pulsars).
It takes the raw data through validation, a leak-free train/test split, tuned Random Forest
training, evaluation on imbalance-aware metrics, a **promotion gate** that decides whether a
new model may replace the current one, and a study of how much training data k-means
sampling can save. An optional **Spark MLlib** implementation is checked against the
scikit-learn one and benchmarked as the data grows.

> **Background.** This started as a coursework exercise in an MSc in Data Science and
> Machine Learning (Hellenic Open University) and was re-engineered into a tested,
> configurable, containerised pipeline. 

## What it does

| Stage | What happens | Code |
|---|---|---|
| Ingest | Downloads `HTRU_2.csv` from UCI once, caches the original file, names the columns | `ingest.py` |
| Validate | Fails fast on missing columns, nulls, non-numeric features, unexpected or missing labels, too few rows; reports dtypes, duplicates, class balance, feature statistics | `validate.py` |
| Split | Stratified 80/20 split, then asserts the class balance survived | `split.py` |
| Train | `GridSearchCV` (5-fold stratified, ROC-AUC) over a Random Forest; feature importances | `train.py` |
| Evaluate | Accuracy, ROC-AUC, PR-AUC, per-class precision/recall/F1, confusion matrix on the held-out test set | `evaluate.py` |
| Promote | A model becomes "production" only if it clears a metric floor **and** beats the current production model; every decision is logged | `promotion.py` |
| Sample | k-means representative sampling (k = 5, 10, 25) keeping the class ratio, each tuned and evaluated like the baseline | `sampling.py` |
| Uncertainty | Bootstrap confidence intervals for every metric, plus a paired comparison of each k-means variant against the full-data model on identical resamples | `uncertainty.py` |
| Visualise | Feature importance, variant comparison, t-SNE of the test set | `visualize.py` |
| Spark (optional) | MLlib Random Forest + k-means, a parity check against scikit-learn, and a scale benchmark | `spark_pipeline.py`, `benchmark.py` |

## Quick start

Requires Python 3.9+.

```bash
python -m pip install -e ".[dev]"
python -m pytest            # run all tests
python -m htru2_pipeline    # run the whole pipeline (downloads the data on first run)
```

Everything is configured in [`config/config.yaml`](config/config.yaml): grids, seeds, the k
values, the promotion thresholds. Useful flags:

```bash
python -m htru2_pipeline --skip-kmeans --skip-tsne   # faster run
python -m htru2_pipeline --skip-uncertainty          # skip the bootstrap intervals
python -m htru2_pipeline --refresh                   # re-download the data
python -m htru2_pipeline --spark-parity              # also run the Spark parity check
```

If the download fails (firewall, offline), put `HTRU_2.csv` at `data/raw/HTRU_2.csv` and run again.

### Spark (optional)

Needs Java 17+ on your `PATH`.

```bash
python -m pip install -e ".[dev,spark]"
python -m htru2_pipeline --spark-parity
python -m htru2_pipeline.benchmark --factors 1 10 50
```

The Spark tests skip themselves automatically when `pyspark` or Java is missing, so
`python -m pytest` works on any machine.

PySpark 4.x prints a compatibility warning when used with pandas 3.x; the test suite passes
with it, but if you run into problems, `python -m pip install "pandas<3"` is the first thing to try.

### Docker

```bash
docker build -t htru2-pipeline .
docker run --rm -v "$(pwd)/reports:/app/reports" -v "$(pwd)/models:/app/models" htru2-pipeline
```

```

  run_summary.json

  evaluation/<variant>_metrics.json
  evaluation/confidence_intervals.csv   # bootstrap interval per variant and metric
  evaluation/paired_comparison.csv      # each variant minus the full-data model, with interval

  benchmark.csv               # with the benchmark
models/
  candidates/                 # every trained model
  production/                 # model.joblib, metadata.json, history.jsonl (audit log)
```

## Design decisions

- **Leak-free by construction.** The test set is split off first and never used for fitting,
  scaling or tuning. The t-SNE plot scales the test data with statistics from the *training* set.
- **No scaler in the Random Forest.** Trees split on thresholds, so scaling changes nothing
  (`scale_features` in the config turns it back on). Scaling is applied only where distances
  matter: k-means and t-SNE.
- **PR-AUC alongside ROC-AUC.** With ~9% positives, ROC-AUC can look flattering; precision-recall
  AUC and positive-class precision/recall are more honest.
- **Uncertainty, not just point estimates.** The test set holds only ~330 pulsars, so recall and
  F1 move by a couple of points from sampling noise alone. Every metric gets a percentile-bootstrap
  interval, and variants are compared to the baseline with a *paired* bootstrap (both models scored on
  the same resamples). If the interval of the difference contains 0, the difference is within noise.
- **`class_weight="balanced"`** handles the imbalance without resampling the data.
- **The class ratio is computed, not hard-coded.** The negative:positive ratio is ~9.9; the
  sampling step rounds it to 10 (`ratio_mode: floor` would give 9) so the original balance is
  actually maintained.
- **Promotion gate.** Candidates must clear a floor and beat production by a margin. One
  caveat: the gate reuses the same test set on every run; a production system would add a
  separate validation set to avoid optimistic bias.
- **Config over code.** Every tunable value lives in YAML and is loaded into typed
  dataclasses; unknown keys raise an error instead of being silently ignored.

## About the Spark part

HTRU2 is small: scikit-learn trains on it in seconds and Spark is **not needed**. The Spark
code exists to show the same workflow on a distributed engine, to verify that the two engines
agree, and to measure where Spark starts to pay off.

- **Parity check** trains the Spark RF on the *same* split and compares ROC-AUC, PR-AUC and F1
  with scikit-learn within a tolerance (`spark.parity_tolerance`). It is a sanity check, not an
  equality test, because the algorithms differ internally.
- **Known differences:** Spark caps tree depth at 30 (so "unlimited" becomes 30), its
  `CrossValidator` folds are random rather than stratified, and class balancing uses a weight
  column equal to `n / (n_classes * n_class)`.
- **Benchmark** replicates the data (with small noise) up to millions of rows and times RF
  training and k-means representative selection on both engines. Spark runs in local mode on
  one machine, so read the output as "when does overhead stop dominating", not as a cluster
  benchmark.

## Results

On a stratified 80/20 split (3,580 test rows, ~9% pulsars), the tuned Random Forest reaches ROC-AUC 0.976 (95% CI 0.966–0.985), PR-AUC 0.930 (0.908–0.951), and pulsar-class precision/recall/F1 of 0.876/0.884/0.880. Retraining on only 55–275 k-means representative samples (0.4–1.9% of the training data) leaves F1 unchanged (0.877–0.885; paired-bootstrap differences within ±0.005, none distinguishable from zero). PR-AUC is also indistinguishable for k=5 and k=25, though slightly lower for k=10 (−0.021). The reduced-data models do shift the operating point: precision rises by 0.03–0.05 and recall falls by 0.03–0.04 at the default threshold in all three cases. Intervals come from 1,000 bootstrap resamples of the test set and capture test-set sampling noise only. Integrated-profile excess kurtosis is the most important feature (0.37).

## Limitations

- Single dataset, 8 engineered features; no feature engineering beyond what the dataset ships.
- Tuning uses a small grid, matching the original exercise.
- The bootstrap intervals capture test-set sampling noise only, not variation from retraining
  with other seeds, and with many variants and metrics a few intervals will exclude 0 by chance.
- Impurity-based feature importances can favour high-variance features.
- The Spark benchmark is single-machine.
